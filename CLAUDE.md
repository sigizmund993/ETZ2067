# ETZ — полигон ВсОШ Робототехника 2026-27 (проектный тур)

Проект: 3D-модель полигона по краткому ЕТЗ (техзадание) для проектного тура
ВсОШ по робототехнике, сезон 2026-27. Модель строится в FreeCAD.

## Файлы проекта

- [etz_kratko_26_27_копия.pdf](etz_kratko_26_27_копия.pdf) — исходное ТЗ (23 стр.), источник всех размеров/требований.
- [ETZ_poligon.FCMacro](ETZ_poligon.FCMacro) — **основной скрипт-генератор модели** (Python). Пересобирает документ `ETZ_Poligon` с нуля при каждом запуске (`App.closeDocument` + `App.newDocument`). Правки вносятся сюда, а не руками в .FCStd.
- [ETZ_Poligon.FCStd](ETZ_Poligon.FCStd) — сохранённый документ FreeCAD (результат работы макроса), открыт прямо сейчас в GUI.
- `freecad-mcp.mcpb` — упакованное расширение для Claude Desktop (см. ниже). Выдано пользователю, в репозитории не обязательно хранить дальше.
- `freecad-mcpb/manifest.json` — исходник манифеста, из которого собран `.mcpb` (на случай пересборки, напр. при добавлении auth-токена).

## Что строит макет (ETZ_poligon.FCMacro)

Глобальная СК: начало — левый нижний угол полигона 600×500 мм, X вправо, Y вверх,
Z вверх от поверхности. Координаты поля ЕТЗ (п. 2.2) переводятся через
`field_to_global()`, начало поля O = центр метки ArUco id 27.

Группы объектов в документе:
- **Полигон** (5 объектов) — основание, зона 1 (350×500), зона 2 (верх/низ, 250×80 каждая), область операционного поля (250×330).
- **Операционное поле** (13 объектов) — лист А4-шаблон, чёрные ограничительные полосы, красная сетка 9×6 клеток по 28 мм, чёрные круги Ø6 и зелёные окружности Ø24,5 в центрах клеток + столбец отбоя, три метки ArUco (DICT_4X4_50, id 27/28/29) с чёрными/белыми частями, оси поля.
- **Шашки** (по 2 объекта на штуку: корпус + шайба) — расставляются по списку `CHECKERS` в начале макроса: `(клетка, цвет[, высота_стопки])`. Клетка — `"Б3"` (буква А..Е = ряд, цифра = столбец) или `"Отбой1".."Отбой5"`. Шашка: Ø26×5, крышка 0,8 мм, стенка 0,9 мм; внутри шайба М8 (ГОСТ 6958-78) Ø24×2 с отверстием Ø8,4, прилегает к крышке.

Чтобы переставить/перекрасить шашки или изменить расстановку — правь только список
`CHECKERS` и/или словарь `COLORS` в начале файла, затем пересобери документ (см. ниже).

## Как смотреть внутрь модели (разрезы)

Три способа, от быстрого к основательному:

- **View -> Clipping View** (команда `Std_ToggleClipPlane`) — отсекает
  вид плоскостью X/Y/Z со ползунком смещения. Самое быстрое; геометрию
  не меняет, в документе ничего не появляется. Для «глянуть, как сел
  подшипник» этого обычно хватает.
- **Part workbench -> Part -> Persistent Section Cut** (команда
  `Part_SectionCut`) — режет все видимые тела разом и закрашивает
  срезы, так что разрез читается как настоящий. Создаёт объект в
  документе: когда насмотрелись, панель надо закрыть, иначе объект
  останется и попадёт в сохранённый файл.
- **Part -> Cross-Sections** (`Part_CrossSections`) — строит настоящие
  контуры сечений (можно серию с шагом). Нужен, когда сечение надо
  измерить или вывести в чертёж; для чертежей дальше TechDraw.

Отдельно: пробел скрывает/показывает выделенное тело — иногда проще
спрятать крышку, чем резать.

Из скрипта сечение считается так (этим я и мерил зазоры):

```python
import Part
sl = shape.common(Part.makeBox(300, 300, 0.2, App.Vector(-150, -150, z)))
print(sl.Area / 2, sl.BoundBox)
```

## Как пересобрать модель

Через MCP (`execute_code` на документе, либо headless):
```python
exec(compile(open('/home/semen/ETZ/ETZ_poligon.FCMacro', encoding='utf-8').read(),
             '/home/semen/ETZ/ETZ_poligon.FCMacro', 'exec'), {'__name__': '__main__'})
```
Макрос сам закрывает старый документ `ETZ_Poligon` и строит заново, затем делает
`viewIsometric()` + `ViewFit`. После пересборки стоит сохранить:
```python
App.getDocument('ETZ_Poligon').save()
```

## MCP-подключение к FreeCAD (как это работает)

Установлен официальный **freecad-mcp** (neka-nat, https://github.com/neka-nat/freecad-mcp), версия **0.1.25**. Два независимых компонента:

1. **Аддон внутри FreeCAD** (workbench "MCP Addon") — поднимает XML-RPC сервер
   на `127.0.0.1:9875`. Установлен в
   `~/.var/app/org.freecad.FreeCAD/data/FreeCAD/v1-1/Mod/FreeCADMCP/`
   (FreeCAD запущен как **flatpak**, `org.freecad.FreeCAD`, 1.1.3 — это важно,
   пути Mod/настроек у flatpak свои, см. ниже).
   Автостарт сервера включён через файл настроек аддона:
   `~/.var/app/org.freecad.FreeCAD/data/FreeCAD/v1-1/freecad_mcp_settings.json`
   (`"auto_start_rpc": true`) — сервер поднимается сам при каждом запуске
   FreeCAD, кнопку жать не нужно.
2. **MCP-сервер** `freecad-mcp` (pip-пакет, `pip install --user freecad-mcp`,
   бинарник `/home/semen/.local/bin/freecad-mcp`) — это именно то, с чем
   говорит Claude по протоколу MCP (stdio). Внутри он сам ходит по XML-RPC к
   порту 9875. Нужен Python ≥3.12 (системный `python3` на машине — 3.12.3,
   подходит; Python самого FreeCAD — 3.13, это другое, отдельное окружение).

Эти два компонента общаются только друг с другом через localhost:9875 — FreeCAD
должен быть запущен (с аддоном) **до** того, как Claude дёргает инструменты.

### Как подключено к Claude

Собран и установлен `.mcpb`-бандл (`freecad-mcp.mcpb`, через официальный CLI
`@anthropic-ai/mcpb`, `npx @anthropic-ai/mcpb pack`). В `manifest.json` —
`"server": {"type": "binary", "mcp_config": {"command": "/home/semen/.local/bin/freecad-mcp", "args": ["--only-text-feedback"]}}`.
Код сервера НЕ забандлен внутрь `.mcpb` — манифест просто указывает на уже
установленный путь, это рабочий вариант (`type: "binary"` не обязан быть
внутри архива).

Поставлено пользователем через **Settings → Extensions → install file** в
Claude Desktop (это НЕ обычный open-source Claude Desktop — внутреннее
приложение c "cowork"/"epitaxy"-движком; отдельного CLI `claude` тут нет,
`claude mcp add` не работает, классический `claude_desktop_config.json` с
ключом `mcpServers` тоже не читается — MCP-серверы живут только как
расширения `.dxt/.mcpb` через Settings → Extensions либо как коннекторы из
реестра через Settings → Connectors).

Подключение проверено end-to-end (см. чейнджлог) — Claude Desktop сам
спавнит процесс `freecad-mcp --only-text-feedback` (родитель —
`/usr/lib/claude-desktop/claude-desktop`), тот коннектится к FreeCAD, видит
документ `ETZ_Poligon`.

**Важный нюанс:** список MCP-инструментов сессии Claude фиксируется при
старте. Если FreeCAD только что переоткрыт/переустановлен аддон — новые
инструменты появятся только в **новом чате**, не в текущем.

## Известные нюансы / грабли на будущее

- Flatpak FreeCAD: **не используй `/tmp`** для файлов, которыми обмениваешься
  с процессом FreeCAD — пиши в `/home/semen/ETZ` или другой путь под `$HOME`.
- `pkill -f FreeCAD` в этом окружении почему-то не проходит через
  sandbox-разрешения Bash-тула (тихо фейлится, даёт `Exit code 1` без вывода).
  Используй `kill -9 <pid>` по явным PID из `ps aux`.
- Цвета `ViewObject.ShapeColor` в современном FreeCAD требуют **однородного**
  типа внутри кортежа — либо все int, либо все float, смешивать нельзя.
- Если меняешь `CHECKERS`/геометрию и видишь похожую ошибку — ищи такие же
  смешанные кортежи по аналогии.
- `freecad-mcp` требует Python ≥3.12 на стороне MCP-сервера — это системный
  `python3`, НЕ питон самого FreeCAD (у FreeCAD 1.1 свой встроенный 3.13,
  отдельный от системного).
- Если переустанавливаешь аддон или обновляешь `freecad-mcp` — версии должны
  совпадать (`get_rpc_status` → `version_check`), иначе будет варнинг о
  рассинхроне; после обновления аддона — перезапусти FreeCAD.

(99% занято), полная библиотека ~1 ГБ. Сделано так:
```bash

  https://github.com/FreeCAD/FreeCAD-library.git <path>/Mod/parts_library
cd <path>/Mod/parts_library && git sparse-checkout set "Mechanical Parts/Bearings"
```
Итого 20 МБ. Добавить ещё раздел — `git sparse-checkout add "Mechanical Parts/Pulleys"`
(нужна сеть: blob'ы докачиваются по требованию).

Грабли:
- `get_parts_list` фильтрует по расширению **`.FCStd` с учётом регистра**, а в
  библиотеке половина файлов названа `.fcstd` строчными — в списке их не видно,
  но `insert_part_from_library` по явному пути их открывает нормально.
  Пример: `Mechanical Parts/Bearings/608ZZ_Ball_Bearing.fcstd`.
- `insert_part_from_library` делает `mergeProject`, то есть вываливает в корень
  документа всю внутреннюю требуху файла (у 608ZZ это `Sketch` + `Revolution` +
  `Chamfer` — PartDesign-фичи без Body). Для покупной детали параметрика не
  нужна: проще скопировать `.Shape` в `Part::Feature` и удалить merge-мусор.
- Шейпы в библиотеке не обязаны стоять осью по Z (у 608ZZ ось вдоль **Y**),
  и своя ориентация у них зашита в `Shape.Placement`. Если присвоить
  `Shape.Placement` новое значение — исходный поворот теряется; нужно либо
  домножать на старый, либо задавать поворот явно.

## Параметрический привод руки (shkiv_param.FCMacro)

[shkiv_param.FCMacro](shkiv_param.FCMacro) строит ведомый шкив GT2 с седлом
под трубу руки и отдельную прижимную крышку. Все размеры живут в объекте
**VarSet `Drive`** в дереве документа `ETZ_Robot` — после
первой сборки макрос не нужен, геометрия меняется правкой переменных в GUI.

Ключевые связи (выражениями, пересчитываются сами):
- `Ratio` -> `DrivenTeeth = round(DriverTeeth * Ratio)` -> делительный Ø,
  вершины, фланцы, `Occurrences` кругового массива зубьев;
- `Ratio` + `BeltLength` -> `CenterDist` (решение формулы длины ремня) ->
  `Part002.Placement.Base.x/y` (`PulleyAxisX`, `ArmAxisY`), то есть весь узел
  отъезжает от вала левого мотора — вперёд и на пол-шага моторов в сторону;
- `BeltPlaneZ` -> `Part002.Placement.Base.z`, венцы ведущего и ведомого совпадают;
- `TubeOD` -> жёлоб седла, крышка, положение и Ø винтов хомута;
- `WindowCount`/`WindowAngle` -> окна облегчения. Фаза первого окна считается как
  `180/WindowCount - WindowAngle/2`, поэтому спица **всегда** приходится ровно под
  седло руки, а не под окно, при любом числе окон.

Крепёж хомута: винт идёт сверху через зенковку в крышке и затягивается в
гайку M3, лежащей в пазу седла (паз открыт на боковую грань, гайка заводится
сбоку). Тянущее усилие держит потолок паза; подошвы под гайкой нет — там,
где седло свисает за фланец, её было бы не на чем печатать.

### Проставка под второй шкив

Отдельное тело `Проставка_шкивов` (`Body_Prost`, фичи с префиксом `S_`) —
труба Ø13/Ø9, садится на верх ступицы первого шкива и поднимает второй
шкив выше крышки хомута, чтобы тот её не задевал. Высота считается сама:
`SpacerH = Pulley2Z - PulleyH`, то есть ровно до низа подшипника
второго шкива.

Сверху проставка упирается во **внутреннее кольцо** подшипника 2
(контакт на R 4.5..6.5, кольцо там есть), а до самого шкива 2 ей 4.5 мм —
то есть о вращающуюся деталь этот торец не трётся. Снизу она всё же
лежит на ступице первого шкива, а та вращается: одна трущаяся пара
остаётся.

Внутренний Ø проставки (`SpacerID`) и отверстие в ступице (`ShaftHoleD`) —
это **одна ось**, оба по 9 мм: зазор под вал Ø8, на котором сидит 608ZZ.
Значения независимы, но макрос печатает предупреждение, если они
разошлись.

### Второй ведомый шкив с рычагом

Отдельное тело `Шкив_ведомый_2` (`Body_Pulley2`, префикс фич `Q_`) сидит
на проставке над первым. Хомута, седла и крепежа у него нет.

**Верхний шкив полностью независим.** Суффикс `2` = второй шкив, и
каждая его фича ссылается только на такие переменные — проверяется так:

```bash
sed -n '/^def build_pulley2/,/^def lib_rigid/p' shkiv_param.FCMacro \
  | grep -nE "V\}\.(FlangeThk|RimH|PulleyH|WindowRin|WindowRout|WindowAngle|WindowCount|WindowPhase|BrgOD|BrgW|ShaftHoleD|FlangeD|TipD|PitchD2|DrivenTeeth)\b"
```

Пусто — значит ни одной ссылки на первую ступень не осталось.

| что | нижний шкив | верхний шкив |
|---|---|---|
| передача | «1 Передача»: `DriverTeeth`, `Ratio` | «1 Передача 2»: `DriverTeeth2`, `Ratio2` |
| фланцы, венец, подшипник, окна | «2 Шкив» | «2 Шкив 2»: `FlangeThk2`, `FlangeLip2`, `BeltWidth2`, `BrgOD2`, `BrgW2`, `ShaftHoleD2`, `WindowCount2`, `WindowAngle2`, `WindowGapIn2`, `WindowGapOut2` |
| расчёт зубьев/Ø | «5 Расчёт» | «5 Расчёт 2» |
| габариты | «6 Производные» | «6 Производные 2»: `RimH2`, `PulleyH2`, `WindowRin2`, `WindowRout2`, `WindowPhase2`, `ShoulderThk2` |

Шаг ремня (`BeltPitch`) и профиль GT2 общие — предполагается один и тот
же тип ремня. Ширина ремня у ступеней уже своя.

Макрос предупреждает, если `ShoulderThk2` ушёл в ноль (подшипник не во что
упереть) или если `BrgOD2`/`BrgW2` перестали быть 608ZZ — тогда
деталь из библиотеки в гнездо не сядет.

Межосевое **общее**: шкивы соосны, поэтому `CenterDist` задаёт первая
ступень (через `BeltLength`), а для второй уже считается, какой ремень
нужен — `BeltLength2`. Шаг и ширина ремня общие: предполагается один и
тот же профиль GT2 на обе ступени.

Если второй мотор встанет не рядом с первым, а со сдвигом, межосевое у
второй ступени станет другим — тогда понадобится свой `MezhOs2`.

Рычаг — **утолщение нижнего фланца вниз**: его верхняя грань совпадает
с верхней гранью фланца, дальше он растёт вниз. Поэтому толщину рычага
можно менять не оглядываясь на ремень: ремень идёт выше, между фланцами,
а под фланцем свободно. Проверено срезами — на высоте полосы ремня
материал шкива кончается на вершинах зубьев (R 31.58), рычага там нет.

Вся высота второго шкива считается от одного требования — рычаг не
должен задевать крышку хомута:
`Pulley2Z = TubeAxisZ + CapThk + SpacerGap + LeverThk - FlangeThk`,
а `LeverZ` (низ рычага, самая низкая точка шкива 2) и `SpacerH`
выводятся уже из него. Утолщишь рычаг — вверх уедет и фланец, и
проставка подрастёт.

Порядок в списке `DERIVED` важен: `ensure_varset()` ставит выражения по
очереди с `recompute` после каждого, поэтому свойство должно появиться
раньше тех, что на него ссылаются — `Pulley2Z` стоит до `LeverZ` и
`SpacerH`.

Размеры рычага — группа «4 Рычаг»: `LeverLen` (до центра отверстия),
`LeverWidth`, `LeverThk`, `LeverHoleD`, `LeverAngle`. Пятка рычага
(`RychagStupica` = `SpacerOD/2 + 1`) заведомо шире проставки, чтобы та
опиралась на неё целиком при любой ширине рычага.

`LeverAngle` поворачивает **всё тело** второго шкива, а не только рычаг.
Так и задумано: окна проворачиваются вместе с ним, спица остаётся ровно
под рычагом, а для шкива поворот безразличен — он всё равно вращается.

Высоты считаются цепочкой: `SpacerH` поднимает проставку до верха
крышки хомута плюс `SpacerGap`, `Pulley2Z` = верх проставки +
`LeverThk`, `BeltPlaneZ2` — куда ставить второй ведущий шкив на мотор
(при текущих числах венец на z 85..92 в глобальных, против 52..59 у
первого).

Подшипник второго шкива — как у первого: гнездо открыто **вниз**
(`BrgZ2 = Pulley2Z`), сверху остаётся упор толщиной
`PulleyH - BrgW` = 3 мм с отверстием `ShaftHoleD` Ø9. Поэтому
рычаг и не доходит до центра: он начинается с `LeverR0 = BrgOD/2 + 2`
= R13, иначе перекрыл бы гнездо снизу. Держится он на фланце — 20 мм
нахлёста по радиусу. Оба 608ZZ ставит `build_bearings()` из библиотеки.

Прежний `Brg608ZZ`, вставленный руками, удалён — его геометрию
один в один повторяет `BRG_1` из макроса (z 0..7, R 11, V 2242.9 мм3),
зато теперь оба подшипника появляются при сборке с нуля.

Ближняя к центру пара винтов (`ScrewX1`) сверлится **насквозь через весь
шкив** — винт может выходить за гайку, поэтому его длина перестаёт быть
критичной. Дальняя пара (`ScrewX2`) висит за фланцем, там сверлить нечего,
и её отверстие остаётся глухим на 2 мм ниже гайки. Условие в
`build_pulley()` — флаг `skvoz`. Проверено: сквозное отверстие оставляет
1.93 мм стенки до границы окна облегчения, 7.84 мм до гнезда подшипника.

Сквозных вырезов доступа под гайки в шкиве НЕТ. Пробовались, но
прямоугольный вырез пересекал наклонную границу окна облегчения и оставлял
в окне зуб ~2x1 мм. Шестигранный вырез эту проблему снимал, но доступ
оказался не нужен — убрано.

Геометрия собрана на **примитивах PartDesign** (`AdditiveCylinder/Box`,
`SubtractiveCylinder/Box`), а не на эскизах: у примитива каждый размер — своё
свойство под выражение, и нет зависимости от имён рёбер.

`pulley_100t.FCMacro.superseded` — прежняя непараметрическая версия. Не
запускать: она перестроит то же `Body003` жёстко заданными числами и снесёт
всю цепочку с выражениями.

### Труба руки — отдельный парт

Труба живёт в своём контейнере `App::Part` «Труба_руки» (`Part_Tube`), а
не в приводе: это отдельная покупная деталь, её удобно двигать и считать
саму по себе. Внутри тело `Труба_Ø10` (`Body_Tube`, префикс фич `T_`) —
цилиндр минус цилиндр, то есть именно труба со стенкой `TubeWall`, а не
пруток.

Placement парта привязан к тем же переменным, что и привод
(`CenterDist`, `BeltPlaneZ - FlangeThk`), поэтому труба едет вместе с
узлом. Начинается она с `ClampStartR`, то есть ровно от начала хомута:
при `ClampLen` = 30 в хомуте сидит 30 мм трубы. Жёлоб седла и крышки
сделан ровно по `TubeOD`, так что зазор 0 — посадка в обхват.

### Локоть: шарнир на подшипнике

Шесть печатных тел в парте «Труба_руки» плюс крепёж:

| тело | что делает |
|---|---|
| `Body_Elbow` + `Body_ElbowCap` | хомут на торце первой трубы, несёт проушину шарнира |
| `Body_Elbow2` + `Body_Elbow2Cap` | хомут на второй трубе, вращается на подшипнике |
| `Body_Tube2` | вторая труба, проходит хомут 2 насквозь |
| `Body_RodJoint` + `Body_RodJointCap` | шарнир тяги на свободном конце трубы 2 |
| `PV_Brg` / `PV_Screw` / `PV_Nut` | 623ZZ, винт M3 сверху, гайка в пазу проушины |
| `Body_Rod` | тяга параллелограмма между рычагом и шарниром |
| `EH_*` (24 шт) | винты M3x16 + гайки всех трёх хомутов локтя |
| `RD_*` (4 шт) | пальцы тяги M3x10 с гайками |

Винт идёт **сверху**: головка прижимает внутреннее кольцо к проушине
хомута 1, гайка сидит в пазу под проушиной. Наружное кольцо
запрессовано в гнездо хомута 2 (Ø`PivotBrgOD` x `PivotBrgW`), поэтому
хомут 2 вращается свободно, а винт ничего к нему не притягивает.
Хомуты труб — винты M3 по той же схеме, что хомут на шкиве: по 4 винта,
гайки в пазах на нижней грани, зенковки в крышках. Сами винты и гайки
стоят в модели — см. «Крепёж хомутов локтя» ниже.

**Локальные координаты обоих хомутов: начало — ось шарнира**, труба идёт
по локальному X, её ось на локальном z = 0. Поэтому хомут 2 с крышкой и
трубой поворачивается простым `Placement.Rotation.Angle` =
`Tube2Angle` — ось вращения проходит ровно через ось шарнира.

Вылет второй трубы считается **от оси шарнира**, и мерится он до
**оси пальца тяги**: палец стоит ровно на `LeverLen`, то есть вылет
равен рычагу на втором шкиве по построению — это и есть условие
параллелограмма. Мерить вылет от грани хомута было ошибкой: длины
звеньев в механизме считаются между осями.

Сама труба до пальца не доходит: `Tube2X0 = -LeverLen + JointReach`,
дальше её продолжает планка проушины (см. ниже). Если бы труба шла до
самого пальца, планку пришлось бы вести внутри неё.

Оси труб разведены по высоте: вторая идёт НАД шарниром,
`Tube2Z = TubeAxisZ + PivotBrgW + PivotCeil + TubeOD/2`.

`ElbowEndX = max(PivotGap + PivotLugR; ElbowHalfW + 1)` — проушина
отодвинута от торца первой трубы не меньше, чем на полуширину хомута 2,
иначе тот при повороте наезжает на крышку хомута 1. И `PivotX` считается
через `ElbowEndX`, а не напрямую через `PivotGap`: иначе жёлоб хомута
кончается не там, где труба, и труба врезается в тело.

Углы сейчас: `LeverAngle` = 90°, `Tube2Angle` = **-90°**. При этом рычаг
и вылет смотрят в одну сторону (+Y), отверстие рычага и палец тяги
приходятся на одну и ту же Y, то
есть тяга ровно параллельна плечу и равна ему по длине (`PivotX` =
175.5 мм) — параллелограмм замкнут. Если поставить `Tube2Angle` = +90°,
рычаг и вылет разойдутся в противоположные стороны и тяга пойдёт
накрест. Межцентровое тяги макрос печатает в отчёте — считает его из
обоих углов, так что при любом их изменении видно, какая нужна планка.

#### Шарнир тяги на конце трубы 2

`build_rod_joint()` — хомут (`Body_RodJoint`, префикс фич `Rod_`) с
крышкой (`Body_RodJointCap`, `RdC_`) на свободном конце второй трубы, в
том же локальном фрейме, что хомут 2: начало — ось шарнира локтя,
значит он поворачивается вместе с предплечьем (`Tube2Angle`).

**Проушина лежит ровно в полосе рычага** — это и был смысл: не 2 мм
перекоса, как раньше, а `JointPlateZ = LeverZ - Tube2Z`, то есть
полоса `z LeverZ..LeverZ + LeverThk`. Проверено: ось отверстия рычага
и ось пальца тяги обе вертикальны, обе в полосе z 79.5..83.5, разнесены
ровно на `PivotX` = 175.5 мм. Тяга — плоская планка с двумя Ø`LeverHoleD`,
гнуть её не нужно.

Размеры проушины повторяют глаз рычага: `JointEyeR = max(LeverHoleD/2 +
JointWall; LeverWidth/2)`, толщина = `LeverThk`. Сечение через палец —
35.2 мм2, по 4.4 мм материала с каждой стороны, как у рычага.

Планка входит в **торцевую стенку** хомута толщиной `JointWall`: хомут
начинается на `JointWall` раньше торца трубы, поэтому стык объёмный, а
сечение в нём 151 мм2 — не «шейка» по касательной. Жёлоб под трубу
режется ПОСЛЕ планки, поэтому там, где планка попала в зону трубы,
материал уходит сам.

Проверки в отчёте макроса: полоса рычага должна лежать между низом
хомута и осью трубы 2 (иначе планка либо оторвётся от стенки, либо
полезет в крышку), а `JointGrip + JointWall` должны влезать между
локтем и пальцем.

#### Тяга

`build_rod()` строит `Тяга` (`Body_Rod`, префикс фич `Tg_`) — плоскую
планку между отверстием рычага и пальцем шарнира тяги, плюс два пальца
M3 с гайками (`RD_*`).

Тело строится вдоль своего локального +X от первого пальца, а оба конца
находит само:

| | что |
|---|---|
| `RodAX`/`RodAY` | отверстие рычага: `LeverLen` под углом `LeverAngle` |
| `RodBX`/`RodBY` | палец шарнира: `PivotX` минус `LeverLen` под `Tube2Angle` |
| `RodLen` | расстояние между ними — длина планки |
| `RodAngle` | `atan2` между ними — куда смотрит планка |

Поэтому при повороте рычага или предплечья тяга поворачивается и
растягивается сама. **Параллелограмм замкнут, когда `RodLen == PivotX`**
— макрос это печатает и предупреждает, если разошлось. Сейчас: 175.50
против 175.50, угол 0°.

Тяга идёт **СНИЗУ**: над рычагом фланец шкива, над проушиной крышка
хомута, а снизу свободно. Верх тяги = низ рычага (`RodZ = LeverZ -
RodThk`), то есть скользящий контакт — так плоские тяги и работают, в
проверке это нулевой зазор без пересечения объёмов.

Ширина планки = `2 * RodEyeR` = `LeverHoleD + 2 * RodWall` (8.2 мм) —
нарочно меньше проушины шарнира (12 мм), иначе планка упиралась бы в
торцевую стенку хомута тяги. Сейчас там 1.9 мм зазора.

Палец: винт M3 сверху через рычаг (или проушину) и тягу, гайка под
тягой. Длина считается как `LeverThk + RodThk + NutThk` -> M3x10.

`atan2` в выражениях FreeCAD есть и принимает ';' как разделитель:
`atan2(dy; dx)`, на выходе угол. Проверял отдельным пробным свойством,
прежде чем ставить в модель — сломанное выражение отравляет весь
документ, и чинить потом пришлось бы исправное.

#### Крепёж хомутов локтя

`build_elbow_hw()` ставит **все** винты и гайки трёх хомутов (локоть 1,
локоть 2, тяга) — по 4 винта M3x16 с гайками, префикс `EH_`. Схема как
на хомуте шкива: головка на дне зенковки (`CapThk - CapWall`), гайка на
низу хомута (`-ElbowBot`), резьба проходит гайку насквозь с запасом
3 мм. Длина выбирается из того, что есть в библиотеке:
`need = CapThk - CapWall + ElbowBot`.

Хомут 2 и хомут тяги **повёрнуты** на `Tube2Angle`, а крепёж живёт в
координатах парта, поэтому положение каждого винта — выражение с
поворотом:

    x = PivotX + lx * cos(a) - ly * sin(a)
    y =          lx * sin(a) + ly * cos(a)

Гайку тоже надо доворачивать на `Tube2Angle`: шестигранник паза
повёрнут вместе с телом, а у гайки симметрия 60°, так что -90° её не
спасают — без доворота она упирается вершинами в грани паза.

Проверено: все 24 детали без пересечений, зазор винта в отверстии
0.2 мм, гайки в пазах 0..0.15 мм, и у каждого паза есть потолок
23.6 мм2 — то, за что гайка тянет.

**623ZZ в библиотеке — упрощённый.** Это просто кольцо Ø10/Ø8 x 4
(объём 110.3 мм3 против 113.1 у такого кольца), внутреннего кольца и
шариков нет, отверстие Ø8 вместо Ø3. На геометрию печатных деталей это
не влияет (гнездо Ø10 x 4 и отверстие Ø3.4 в проушине — под настоящую
деталь), но в модели винт M3 болтается в Ø8, и зазор «винт -
подшипник» показывает 1.25 мм вместо нуля.

**Ось библиотечной детали может сидеть в `Shape.Placement`.** У 623ZZ
сырая геометрия смотрит по Z и лежит в z 0..4 — ровно как нужно для
вертикального шарнира, а собственный Placement разворачивает её на Y.
Я сначала этого не заметил, и подшипник лёг на бок, дав три ложных
пересечения сразу. Для таких деталей Placement надо сбрасывать, а не
домножать.

**Проверяйте, что все имена из выражений объявлены.** Опечатка в
`{V}.Name` всплывает не как ошибка макроса, а как `Invalid` на фиче, и
диагноз виден только в `obj.getStatusString()`:
`Property 'X' not found in 'Drive.X'`. Готовая проверка:

```bash
python3 - <<'EOF'
import io, re
s = io.open("shkiv_param.FCMacro", encoding="utf-8").read()
used = set(re.findall(r"\{V\}\.([A-Za-z_][A-Za-z0-9_]*)", s))
decl = set()
for b in ("INPUTS", "DERIVED"):
    m = re.search(r"^%s = \[(.*?)^\]" % b, s, re.S | re.M)
    decl |= set(re.findall(r'^\s*\("([A-Za-z_][A-Za-z0-9_]*)"', m.group(1), re.M))
print("НЕ ОБЪЯВЛЕНЫ:", sorted(used - decl) or "нет")
EOF
```

### Правый мотор и вторая ступень

`build_motor2()` ставит `Мотор_NEMA17_правый` в точку
(`Motor2X`, `Motor2Y`, `Motor2Lift`) и вешает на него ведущий шкив
второй ступени.

**Компоновка: моторы бок о бок ПОЗАДИ руки.** Рука смотрит вдоль +X от
оси шкивов, поэтому моторы стоят по другую сторону от неё — в сторону
−X. Двигается при этом не мотор, а узел руки: левый мотор — начало
координат документа, и всё остальное считается от него.

    MotorPitch  = MotorSize + MotorGap          (42.3 + 3 = 45.3)
    ArmAxisY    = MotorPitch / 2                (ось руки ровно посередине)
    PulleyAxisX = sqrt(CenterDist^2 - ArmAxisY^2)
    Motor2X     = PulleyAxisX - sqrt(CenterDist2^2 - ArmAxisY^2)
    Motor2Y     = MotorPitch

Ось шкивов уезжает в (`PulleyAxisX`, `ArmAxisY`) — ровно на середину
между валами моторов, поэтому оба ремня симметричны, а рука выходит
между моторами. Оба межосевых при этом соблюдаются точно: проверено,
77.6513 против расчётных 77.6513 у обеих ступеней.

Плотность задаётся одним `MotorGap`: при равных ремнях
(`CenterDist == CenterDist2`) `Motor2X` выходит нулевым, то есть валы
встают на одну линию поперёк руки, а корпуса — с зазором ровно
`MotorGap` (проверено: 3.000 мм). Если ремни разной длины, второй мотор
сам отъезжает назад по X.

Требование `CenterDist >= ArmAxisY` (и то же для второй ступени) —
иначе корень уходит в минус; `max(...; 0)` не даёт nan, а макрос печатает
предупреждение. `BeltSlack2` показывает запас длины ремня,
`TeethInMesh2` — зубья в зацеплении, обе считаются от `CenterDist2`.

Ремни не модельные, но их огибающую можно построить выпуклой оболочкой
двух окружностей по вершинам зубьев и измерить зазоры — так проверено,
что ремень 1 проходит мимо корпуса второго мотора с 5.5 мм, а ремень 2
мимо крышки хомута с 6.0 мм.

По высоте мотор поднят на `Motor2Lift = BeltPlaneZ2 - FlangeThk`.
Шкив — не копия, а **`App::Link`** на существующий
`Шкив_ведущий_20T` с `LinkTransform = True`: оригинал сделан эскизами с
жёстко заданными 20 зубьями, копировать геометрию незачем, а правка
оригинала отразится на обоих. Положение мотора и шкива держат одни и те
же `Motor2X`/`Motor2Y`/`Motor2Lift`.

Проверено: венец ведущего 2 встал на z 83.50..90.50 — ровно на венец
верхнего ведомого, как венец ведущего 1 (z 52.00..59.00) совпадает с
нижним.

Если поменять `DriverTeeth2`, расчёт второй ступени разойдётся с
геометрией эскизного шкива — макрос про это предупреждает.

**Как мерить глобальные координаты у `App::Link`.** У него нет
`getGlobalPlacement()`, и у ссылки с `LinkTransform = True` собственный
Placement домножается на Placement оригинала — вручную это легко
посчитать неверно (я сначала получил z 31.5 вместо 75.5). Правильно
спрашивать форму у Part:

```python
Part.getShape(obj, "", needSubElement=False, transform=True)
```

Это даёт форму с собственным Placement объекта, но **без** Placement
родительских `App::Part` — их надо домножить отдельно, обойдя `InList`.

### Грабли движка выражений FreeCAD

- **Имя свойства не должно совпадать с обозначением единицы.** Свойство с
  именем `C` (кулон) ломает любое выражение, которое на него ссылается, —
  с бесполезным сообщением «Expression can not evaluate to a value».
  Так же опасны `T`, `N`, `F`, `W`, `J`, `A`, `K`, `S`, `V`, `L`.
- **Одно сломанное выражение отравляет весь документ.** После него *любой*
  последующий `setExpression`/`recompute` возвращает ту же обобщённую ошибку,
  даже для заведомо корректных выражений и в другом объекте. Диагностируя,
  сначала удалите свойство с битым выражением, иначе будете чинить исправное.
- `sqrt` не умеет единицы: пишите `sqrt(X / 1mm^2) * 1mm`.
- `max(a; b)` и `max(a, b)` оба работают. Для формулы межосевого расстояния
  `max(..., 0 mm^2)` обязателен: при слишком коротком ремне подкоренное
  выражение уходит в минус, `sqrt` даёт **nan**, и объект молча уезжает в
  неопределённую точку вместо ошибки.
- Python-число нельзя складывать с `Quantity` — «Unit mismatch in plus
  operation». Берите `.Value`.

### Почему «меняю передачу, а нижний шкив не меняется»

Так было: в `Body003` остались **забытые `PartDesign::Fillet`** от
опытов со скруглениями. Код скруглений я из макроса убрал, а сами фичи
в документе остались, и `Tip` тела указывал на `Fillet009`. При смене
числа зубьев имена рёбер поехали, `Fillet004` стал `Invalid` (его
`Base` показывал `['?Edge33', '?Edge31']` — знак вопроса означает, что
ребро не найдено).

**Одна невалидная фича останавливает пересчёт всего документа.** Тело
остаётся в состоянии `Touched` со старой геометрией, причём молча: в
отчёте ошибки нет, другие тела (например `Body_Pulley2`, собранное
позже) пересчитываются нормально — и выглядит это как «меняется только
верхний шкив». Диагностика:

```python
[(o.Name, o.State) for o in doc.Objects if "Invalid" in o.State or "Touched" in o.State]
```

Лечится так: `body.Tip = <последняя хорошая фича>`, затем удалить
битые фичи с хвоста к началу, затем `doc.recompute()`.

**Удалили фичу, которая была `Tip` — тело исчезает из 3D-вида.**
Тело PartDesign рисует именно `Tip`, а видимость хранится у фичи, не у
тела. После удаления забытых скруглений (они и были `Tip`) новая `Tip`
осталась невидимой, и шкив с крышкой пропали из вида при
`Body.Visibility = True` и совершенно целой форме. Проверка:

```python
[f.Name for f in body.Group if f.ViewObject.Visibility]
```

Должна быть ровно одна видимая фича — текущая `Tip`. В макросе за это
отвечает `show_tip()`, вызывается после сборки каждого тела.

**Ctrl+Z в GUI откатывает и то, что сделано через MCP.** Я работаю в том
же живом документе, поэтому одна отмена снесла разом и удаление
скруглений, и добавленные переменные — выглядело это как «переменных
второй ступени нет вообще». Признак: в `doc.UndoNames` одна-две записи и
вернувшиеся `Fillet*`. Восстанавливается повторным прогоном
`ensure_varset()` + `build_pulley2()`, значения пользователя при этом не
трогаются.

**И проверяйте, что сохранение дошло до диска,** а не только печать
«saved»:

```bash
unzip -p ETZ_Robot.FCStd Document.xml | grep -c Ratio2
```

- **`ensure_varset()` пересчитывает один раз в конце, а не после каждого
  выражения.** На двух телах со 120 зубьями сорок пересчётов подряд
  вешали FreeCAD на несколько минут. Для `setExpression` значение
  свойства не нужно — нужно лишь, чтобы оно существовало, то есть
  достаточно правильного порядка в `DERIVED`.

### Грабли PartDesign/API

- `doc.removeObject(body.Name)` на теле **не удаляет его фичи** — они
  осиротеют. В дереве при этом видно только хвост цепочки (фичи показывают
  свой `BaseFeature` как ребёнка), поэтому чистить надо слоями, пока не
  кончатся. См. `purge_orphans()` в макросе.
- **`transformGeometry` — не для жёсткого поворота.** Он пересобирает
  поверхности в B-сплайны. На 608ZZ от этого объём уехал на 1%,
  цилиндрические грани исчезли (`GeomCylinder` -> `BSplineSurface`), а
  `BoundBox` стал считаться по контрольным точкам и показывал
  33x38x7 вместо 22x22x7 — то есть по габаритам деталь выглядела
  повёрнутой, хотя дело было в аппроксимации. Для поворота/сдвига есть
  `lib_rigid()`: Placement шейпа сохраняется как есть, `Part::Feature`
  наследует его вместе с разворотом.
- `obj.getGlobalPlacement()` **уже включает** собственный `Placement`
  объекта, а у `Part::Feature` `Shape.Placement` — это он же. Перемножать
  их нельзя: получите двойное смещение и ложные «пересечения» при проверке
  сборки. Правильно:
  `shape.Placement = obj.getGlobalPlacement() * obj.Placement.inverse() * shape.Placement`.

### Скруглений в модели нет — и почему не стоит пробовать снова

`PartDesign::Fillet` по стыку седла и шкива пробовался и **снят**. Если
соберётесь повторить — вот что выяснилось, чтобы не ходить по кругу.

Корень седла стоит над окном облегчения, поэтому линия стыка разорвана:
её куски — короткие диагонали по наклонной границе окна (3.8 мм) вперемешку
с обрезками по 0.2–0.4 мм. На таких рёбрах галтель не встаёт **ни на каком
радиусе** (проверено до 0.25 мм), не встаёт и фаска, и не помогает подача
всей цепочки разом: материала под ребром местами просто нет.

Что при этом ломалось:

- **Нумерация рёбер меняется после каждого скругления.** Нельзя собрать
  список `Edge*` один раз и применять дальше по цепочке: индексы начинают
  указывать на другие рёбра. У меня так скруглились ребро на верхней грани
  седла и зуб на нижнем фланце. Искать кандидата надо заново в текущем
  `body.Tip`, помечая обработанные по координате середины ребра.
- **Подбирать рёбра до `recompute` бесполезно** — у только что созданной
  фичи `Shape` не посчитан, список рёбер пуст.
- **`f.State` и `Shape.isValid()` не ловят брак.** Скругление рапортует
  успех, проходит проверку и портит форму на следующем пересчёте;
  `Shape.check()` потом бросает `Unorientable shape`. Нужен финальный проход
  по готовому телу.
- **Дно гнезда гайки лежит в той же плоскости стыка.** Если не исключить
  его из отбора, галтель нарастит материал внутрь гнезда и гайка
  перестанет влезать.
- Каждая попытка — два пересчёта тела со 100 зубьями, то есть полная
  пересборка с перебором рёбер занимала **около 6 минут**.

Единственное, что реально убирало причину, — сдвинуть `ClampStartR` до 18,
чтобы подошва седла целиком легла на спицу. Тогда диагонали исчезают и
стык скругляется штатно. Но это двигает хомут на 5 мм наружу.
